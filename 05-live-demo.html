Agenda / Session 5

05 Live Demo: From Business Requirement to Production

14:45–15:4560 minLive demo

Experience an end-to-end application development journey, starting from a business requirement and progressing through AI-assisted development, code review, security validation, CI/CD, and application deployment.

Key message

One business requirement reaches production in an hour: AI does much of the work, while people decide, review and approve, and the platform enforces quality and security at every step.

What the audience will see
  • A requirement turned into an issue and sub-issues with Copilot
  • Code written in VS Code agent mode and, in parallel, by the Copilot cloud agent
  • Copilot code review, human approval, CodeQL with Copilot Autofix, dependency review
  • CI/CD with GitHub Actions to Azure App Service, using OIDC and an approval gate
Names used in this runbook

Organization contoso, repository contoso-order-desk, Azure web app contoso-order-desk-demo. Replace them with your demo organization and resources. The environment build is in the facilitator guide; rehearse the full run at least twice.

The story

Business requirement · Contoso Retail customer service

"Our agents answer a lot of where is my order? calls, and today they search several systems to find one order. We need a simple Order Desk: an agent types an order number and immediately sees the order status and estimated delivery date. Unknown or mistyped numbers must show a clear message. Agents must not see payment details, and every lookup must be recorded for audit."

Cast
  • Presenter (developer and requester): drives VS Code, creates issues and assigns work to Copilot.
  • Approver (reviewer and release manager): a second person with write access, on a second laptop or browser profile. They approve pull requests, workflow runs and the production deployment.
  • Narrator (optional): keeps time and links each step back to Sessions 1–4.

Two people are required, not just nice to have. The person who asks Copilot for work cannot approve the resulting pull request, and Actions workflows on Copilot's pull requests wait for approval from a user with write access.

Pre-flight · 30 minutes before

  • Presenter signed in to GitHub (browser profile A) and VS Code; Approver signed in on a second laptop or browser profile B.
  • main is reset to the demo-start tag, and rehearsal issues are closed. The Project board shows no rehearsal items.
  • Security pull requests opened at least 30 minutes earlier, with checks finished: demo/not-found-message (CodeQL alert) and demo/add-date-helper (dependency review failed).
  • Fallback branches exist: fallback/order-lookup-api and fallback/agent-lookup-page, plus the rehearsal cloud agent pull request kept as a draft.
  • The Azure web app opens, and the last production deployment is green.
  • VS Code: font size 18 or larger, Agent and Plan modes visible, npm ci done, a terminal open in the repository.
  • Tabs open: repository, Project board, Actions, Settings → Rulesets, Security and quality tab, Azure portal (web app).
  • Notifications off, display tested, a visible timer, and the rehearsal recording on hand in case the network fails.
1

Requirement → issue

3–10 min
  1. Create the issue with Copilot. Open github.com/copilot and paste the requirement with this prompt. Copilot maps it to the repository's issue form and can draft sub-issues. Public preview
    Prompt · Copilot on GitHub.com

    In contoso/contoso-order-desk, create a feature issue from the requirement below using our Feature request form. Write testable acceptance criteria, and create sub-issues for: (1) the order lookup API, (2) the agent lookup page, (3) an audit log of every lookup. [paste the business requirement]

    A draft parent issue with the form's sections filled in, plus three sub-issues to review before you create them.
  2. Review before creating. Read the acceptance criteria aloud and fix one by hand. The point is that people own the requirement.
  3. Show the plan. Open the Project board: the issue arrived through the form's projects key or the project's auto-add workflow. Set the issue type to Feature and move it to In progress.
  4. Delegate the page now, so it is ready by Act 3. Open sub-issue (2), choose Assignees → Copilot and add this optional prompt:
    Optional prompt · assigning to Copilot

    Build the agent lookup page in public/ with plain HTML, CSS and JavaScript. Another pull request is building the API; code against this contract: GET /api/orders/:orderId returns 200 with { id, status, lastUpdated, estimatedDelivery }, 400 for invalid IDs and 404 with { error } when not found. Show a clear message for unknown order numbers, make the form keyboard accessible, and add tests.

    An 👀 reaction, then a draft pull request in the issue timeline and a "Copilot started work" event with View session.
Say

"The issue is the contract. People and agents work from the same acceptance criteria, and Copilot reads only what is in the issue when you assign it, so later comments go on the pull request."

If it goes wrong

If creating issues with Copilot is unavailable or slow, use New issue → Feature request and paste the prepared text. The demo still works.

2

Build with AI in VS Code

10–24 min
  1. Set context. Create branch feature/order-lookup-api. Open .github/copilot-instructions.md for ten seconds: "these are Contoso's rules, and every Copilot surface reads them."
  2. Plan first. In Chat, choose Plan:
    Prompt · Plan mode

    Plan the order lookup API from issue #<API sub-issue>: GET /api/orders/:orderId returns id, status, lastUpdated and estimatedDelivery from data/orders.json; 400 when the ID doesn't match ORD- plus six digits; 404 with a JSON error for unknown IDs. List the files you will change and the tests you will add.

    A plan naming the files to change (for example, an orders module, the app routes and a test file) and the test cases. No files changed yet.
  3. Let the agent work. Switch to Agent:
    Prompt · Agent mode

    Implement the plan. Then run npm test and fix any failures.

    Edits across files, then a request to approve npm test in the terminal. Approve it, and the tests pass (or the agent fixes them and reruns).
  4. Review the diff like a senior engineer. Check the validation regex and the 404 body. Undo or adjust one thing by hand.
  5. Commit and open the pull request. Let Copilot suggest the commit message. Push, open a pull request with Fixes #<API sub-issue>, and let Copilot write the summary.
Say

"Agent mode did the typing and ran the test loop. I chose the design, approved every command and reviewed the diff."

If it goes wrong

If the agent stalls or tests keep failing after two rounds, stop. Check out fallback/order-lookup-api, push it and open the pull request. Say so openly: "this is the rehearsal run of the same prompt."

3

Review: Copilot first, people decide

24–32 min
  1. Copilot code review. On the API pull request, Copilot was requested automatically by the ruleset (or choose Reviewers → Copilot). Read one comment aloud and apply a suggestion, or use Fix with Copilot. A "Comment" review from Copilot, usually in under 30 seconds. It does not count toward required approvals.
  2. Open the cloud agent's pull request. Show View session: the agent's reasoning, the tools it ran and its self-checks (CodeQL, secret scanning, dependency check). Show that commits are signed and list the presenter as co-author.
  3. Approver: approve and run workflows. Workflows on Copilot's pull request wait for Approve and run workflows. The Approver clicks it.
  4. Iterate with a comment.
    Pull request comment

    @copilot Show the estimated delivery date in a friendly format such as "5 Nov 2026", and add a test for it.

    Copilot acknowledges, then pushes a new commit to the same pull request.
  5. Human approval. The Approver reviews and approves both pull requests. The presenter cannot approve the Copilot pull request they requested, and that is by design.
Say

"Copilot gives a fast first review, but merging still needs a different human's approval. That is enforced by the platform, not by good intentions."

If it goes wrong

If the cloud agent's pull request is not ready, show its live session log, then review the rehearsal pull request instead. Come back to the live one in Act 5.

4

Security gate in the pull request

32–44 min
  1. Code scanning + Copilot Autofix. Open the pull request from demo/not-found-message, which was opened before the session so CodeQL had time to run. It adds this deliberately unsafe handler: The Code scanning results check reports a cross-site scripting alert on the changed line, with a Copilot Autofix suggestion (typically encoding the output).
  2. Accept the fix. Review the Autofix patch, then commit it to the branch. Wait for the rerun, and the alert closes.
  3. Dependency review. Open the pull request from demo/add-date-helper, which adds an old package version with published advisories: The Dependency Review check fails and lists the advisories. The Files changed tab shows the dependency diff.
  4. The merge gate. Scroll to the merge box: merging is blocked until required checks pass and conversations are resolved. Close the dependency pull request.
  5. Optional (skip if shown in Session 4): push protection blocking a made-up Contoso token from the terminal.
Say

"Security feedback arrives in the pull request, with a proposed fix, before anything merges. The same gates apply to code from Copilot."

Verify in rehearsal (not guaranteed by the docs)

By default the code scanning check fails on error, critical or high findings, and Copilot Autofix covers a subset of CodeQL queries on a best-effort basis. Confirm in rehearsal that this alert fails the check at your thresholds and gets an Autofix suggestion. If it doesn't, adjust the ruleset thresholds or use a higher-severity example. Also confirm the dependency advisories still trigger.

5

CI/CD to Azure App Service

44–54 min
  1. Merge. Squash-merge the API pull request, then the page pull request. Fixes # closes the sub-issues.
  2. Watch the pipeline. In Actions, the CI/CD run on main shows build passing, then deploy waiting for the production environment.
  3. Approver approves the deployment (Review deployments → approve). With "Prevent self-review" on, the presenter cannot approve their own deployment.
  4. Show OIDC in the logs. The Az CLI login step signs in with a short-lived token. There is no stored password, and the Azure identity can only deploy to this one web app.
  5. Use the app. Open the environment URL. Look up ORD-100232 (Out for delivery), then ORD-999999 (clear not-found message), then 12345 (invalid format, rejected by the API's validation).
  6. Deployment history. Repository home page → Deployments: each release with its environment, commit and logs. The workflow run records the approval.

Adaptations: OIDC login instead of the publish profile in GitHub's App Service example; Node.js 24; one workflow for CI and CD. Action versions and pinned SHAs are as shown in GitHub Docs on 26 October 2026; update them through Dependabot.

Say

"Azure trusts a short-lived token from this repository's production environment, and nothing else. A person approved the release, and GitHub recorded it."

If it goes wrong

OIDC errors are usually a subject mismatch. The federated credential must match the job exactly (environment:production), and repositories created after 15 July 2026 use a new immutable subject format. Show the last successful deployment and the live site, and fix the credential after the session.

6

Close the loop

54–60 min
  1. Back to the business. The Project board shows the items as Done, and the stakeholder can see the outcome without reading code.
  2. Recap the hour in one line each: requirement → issue (Copilot) → API (agent mode) and page (cloud agent) in parallel → Copilot and human review → CodeQL + Autofix, dependency review → CI/CD with approval and OIDC → live.
  3. The audit trail: signed commits linked to agent session logs, required reviews, deployment approvals and the enterprise audit log, where agent activity can be filtered with actor:Copilot.
  4. Bridge to Session 6: "Sub-issue (3), the audit log, is still open. In the next session we will see what it means to hand whole workstreams like that to agents."

Knowledge check

3 quick questions

Answers come from this page. Nothing is sent anywhere.

  1. How does the deploy job sign in to Azure without a stored password?

    The federated credential trusts only environment:production, and the identity has Website Contributor on this one web app.

  2. Why does the live demo need a second person, the Approver?

    Two people are required, not just nice to have. The Approver also approves the production deployment.

  3. What holds the deploy job until a person approves it?

    Required reviewers are configured on the production environment. With Prevent self-review on, the presenter cannot approve their own deployment.
Presenter tips for a live AI demo
  • Say out loud that AI output varies. "Copilot won't type exactly what it typed in rehearsal; that's normal. Watch how we check it." This turns surprises into credibility.
  • Narrate the decision, not the button. For every step, say who decides (a person) and what enforces it (the platform).
  • Start long-running things early: assign the cloud agent in Act 1, and open the security pull requests before the session.
  • Keep a visible clock. If you are more than 3 minutes behind at minute 24, use a fallback branch for the rest of Act 2.
  • Reset after rehearsal: reset main to demo-start, close rehearsal issues and pull requests (keep one Copilot pull request as a draft fallback), and redeploy the baseline.
  • Afterwards: delete the Azure resource group if the app is no longer needed, and remove the demo custom pattern if it was created at organization level.
