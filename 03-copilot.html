Agenda / Session 3

03 Accelerating Developer Productivity with GitHub Copilot

13:40–14:1030 minTalk + mini demos

See how GitHub Copilot can assist development teams across everyday software engineering activities, helping developers work more effectively while improving the overall developer experience.

Key message

Copilot helps across a developer's whole day, not just while typing. It gets much better when the team writes down its standards once, in files Copilot reads every time.

By the end of this session
  • Developers know which Copilot surface and mode suits which task
  • Tech leads know how to make Copilot follow Contoso's conventions
  • Leaders know the guardrails and cost controls for a rollout

Where Copilot works

Pick the right mode for the task

ModeUse it whenWhat happens
Code completion & next edit suggestionsYou are in flow and know what to writeSuggestions as you type (Tab to accept). Next edit suggestions predict where and what to edit next. Not billed in AI credits on paid plans.
AskYou want to understand code or explore optionsAnswers, explanations and snippets, without changing files.
Edit (VS Code, JetBrains)A quick, controlled change to a defined set of filesYou choose the files and keep granular control of each edit.
PlanThe task is large or ambiguousA plan agent researches with read-only tools and drafts a plan. No code changes until you approve. Not available in Visual Studio.
AgentComplex multi-step work, or tasks that need tools (MCP)Copilot chooses files, edits them, runs commands and iterates. By default you approve commands before they run.
Cloud agentA well-scoped task you can hand offWorks in the background in a cloud environment and opens a pull request for review (Session 6).

Make Copilot follow Contoso's standards

Customization is where a team turns individual productivity into consistent quality. Repository files are versioned, reviewed and shared like code:

File or settingScopeNotes from GitHub Docs
.github/copilot-instructions.mdWhole repositoryCoding standards, frameworks and project context, applied automatically.
.github/instructions/NAME.instructions.mdMatching pathsFrontmatter applyTo: "**/*.ts,**/*.tsx". excludeAgent: "code-review" or "cloud-agent" hides a file from one agent. When a file matches, both repository-wide and path-specific instructions are used.
AGENTS.md (or CLAUDE.md, GEMINI.md)Folder tree; nearest winsRules shared across AI tools. On GitHub.com, path-specific instructions are used only by the cloud agent and code review.
.github/prompts/NAME.prompt.mdInvoked manuallyReusable prompt templates, for example "API security review". Labelled public preview in the IDE how-to.
.github/agents/NAME.agent.mdSelected per taskCustom agents with their own instructions and tools. See Session 6.
MCP serversIDE, CLI, cloud agent, code reviewShare per repository with .vscode/mcp.json. For Business and Enterprise seats, the MCP servers in Copilot policy is disabled by default.
Personal and organization instructionsUser / organizationOrganization instructions (Business, Enterprise) apply to Chat, code review and the cloud agent on GitHub.com. Precedence: personal, then repository, then organization.

Copilot Spaces: shared context for a team

A space collects the context Copilot should use for a topic: repositories, code, pull requests, issues, notes, images and uploads. Anyone with a Copilot licence, including Free, can use spaces. Organization-owned spaces can be shared with admin, editor or viewer access. They work in Chat on GitHub and in the IDE through the GitHub MCP server, and questions consume AI credits. (About GitHub Copilot Spaces)

What not to put in instructions

The docs advise against instructions that only point to an external style guide, or that impose a persona on responses. Write the rules themselves, briefly and directly.

Practices that make the difference

From "Best practices for using GitHub Copilot"

  • Copilot is strongest at tests, repetitive code, fixing syntax, explaining code and regular expressions.
  • Use inline suggestions for snippets and comment-driven code; use Chat for questions and larger sections.
  • Always validate output with tests, linting, code scanning and IP scanning.
  • Keep relevant files open and close irrelevant ones; start a new conversation when old context stops helping.

Best practices for using GitHub Copilot

From "Prompt engineering for GitHub Copilot"

  • Start general, then add specifics; give examples.
  • Break big tasks into small ones.
  • State rules directly rather than as meta-instructions.
  • Put reusable repository context in instruction files, and start a new session for each new task.

Guardrails for an enterprise rollout

ControlWhat it doesWatch out for
Feature and model policiesEnterprise settings override organization settings, or let organizations decide. Organization owners control features under Policies and models beyond the basic set under Models.Within one enterprise, the least restrictive setting usually applies. Some models are disabled by default; use audit logs to spot policy drift.
Content exclusion Business / EnterpriseExcluded files get no inline suggestions, don't inform responses and aren't reviewed. Paths use patterns like "/scripts/**".Not supported in Edit or Agent modes; public preview on GitHub.com and Mobile; changes can take up to 30 minutes to reach IDEs.
Suggestions matching public codeBlock or allow. Copilot compares about 150 characters of surrounding code with public code; matches occur in under 1% of suggestions, and code references help review licensing.The cloud agent and CLI may still generate matching code even when the policy is set to Block.
Data useCopilot Business and Enterprise data is not used to train models and is covered by GitHub's Data Protection Agreement.Free, Pro, Pro+ and Max interactions may be used for training unless the user opts out, so use company-managed seats.
CostAI credits are pooled across the billing entity; budgets per user, cost center, organization or enterprise.Paid usage beyond included credits is on by default. Turn off the AI credits paid usage policy to block it.

Mini demo A · Understand and test legacy code (Ask → /tests)

  1. Open an unfamiliar module in the demo repository. In Ask mode: "Explain the files in this directory."
  2. Select one function: "/tests Generate unit tests for this function." Then follow up: "Add failure and edge cases."
  3. Run the tests in the terminal. Point out that you validate before you accept.

Mini demo B · Plan, then let agent mode do the work

  1. Switch to Plan: "Plan adding input validation for order numbers (ORD- plus six digits) to every route. List files and tests to change."
  2. Approve the plan and switch to Agent. Show it editing files, proposing a terminal command (npm test) and waiting for your approval.
  3. Undo one edit to show the developer stays in control.

Mini demo C · Copilot CLI

  1. In a terminal: copilot, then "My CI is failing on this branch. Fetch the workflow logs and fix the problem." (use a branch with a deliberately failing test).
  2. Show the tool-approval prompt, then /diff before anything is pushed.

Likely questions

  • "Which models can we use?" It depends on plan, client and admin policy. Don't promise specific model names, because the supported list changes often. Choosing Auto gives a discount on paid plans. (Supported AI models in GitHub Copilot)
  • "Do completions use up credits?" No. Code completions and next edit suggestions are not billed in AI credits on paid plans.
  • "Can we stop Copilot from seeing certain files?" Yes, with content exclusion (Business and Enterprise), but note that it does not apply in Edit and Agent modes.
