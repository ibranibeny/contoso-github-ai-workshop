Preparation checklists

Checkboxes are saved in this browser, so you can tick items off as you go.

Two weeks before

  • Confirm date, venue, attendee list and mix (developers, security, platform, IT leaders) with the Contoso sponsor.
  • Ask attendees to bring one or two delivery pain points for Session 7.
  • Confirm licences and policies for the demo organization (see Demo environment).
  • Build the demo repository and the Azure resources; run the first end-to-end rehearsal.

One week before

  • Re-check the watchlist against GitHub Docs and the changelog; update the site if anything changed.
  • Second full rehearsal with the approver; time each act.
  • Record the rehearsal as a backup video.
  • Agree with Contoso IT that the venue network reaches github.com, the GitHub content domains and the Azure portal.

The day before

  • Reset the repository to demo-start; close rehearsal issues; keep one Copilot pull request as a draft fallback.
  • Confirm the web app is up and the last deployment is green.
  • Update VS Code and Copilot; confirm Agent and Plan modes are visible.
  • Print the Session 7 worksheet; prepare sticky notes and dot stickers.

On the day

  • Open the two security pull requests at least 30 minutes before Session 5, so CodeQL and dependency review have finished.
  • Run the demo pre-flight at 12:30 and again during the break.
  • Silence notifications on every presenting machine.

Starter repository

A deliberately small Node.js 24 + Express 5 app, so the demo is about the workflow, not the code. Create contoso/contoso-order-desk with these files, run npm install to create the lock file, run npm test, then commit.

Add a minimal public/index.html placeholder ("Order Desk, coming soon"), because the cloud agent replaces it in Act 1. Then add the configuration files:

  • .github/copilot-instructions.md and .github/instructions/tests.instructions.md (Session 3)
  • .github/ISSUE_TEMPLATE/feature-request.yml, config.yml, .github/CODEOWNERS, .github/workflows/copilot-setup-steps.yml and .github/workflows/ci-cd.yml (Session 5)
  • .github/dependabot.yml and .github/workflows/dependency-review.yml (Session 4)
Starter code not run by us

This starter code was written for this guide but has not been run, because npm install needs network access. Run npm install && npm test in your first rehearsal and fix anything that fails before you tag demo-start.

Repository settings

  1. Security and quality. Enable the dependency graph, Dependabot alerts and security updates, secret scanning with push protection, and CodeQL default setup. Wait for the first successful CodeQL run, because alerts appear only after it.
  2. Custom pattern for the push protection demo: contoso_demo_[a-z0-9]{32}; dry run, publish, enable push protection (Session 4).
  3. Ruleset on main (Settings → Rules → Rulesets → New branch ruleset):
    • Require a pull request before merging: 1 approval, review from Code Owners, dismiss stale approvals, require conversation resolution
    • Require status checks to pass: build and dependency-review (run each workflow once first so the checks can be selected)
    • Require code scanning results: CodeQL
    • Automatically request Copilot code review, with Review new pushes on
    If a rule turns out to be incompatible with the cloud agent, GitHub Docs suggest adding Copilot as a bypass actor for that ruleset.
  4. Environment production: required reviewer = the approver; Prevent self-review on; deployment branches = main only. Create it before the first deployment, because a workflow that references a missing environment creates one with no protection rules.
  5. Copilot settings: leave the cloud agent firewall on with the recommended allowlist, and validation tools (CodeQL, secret scanning, dependency checks) on. Run Copilot Setup Steps manually once from the Actions tab to check it.
  6. Project: create "Order Desk" with a Status field, the auto-add workflow for this repository, and the "item closed → Done" workflow.

Azure resources and OIDC

Follows Microsoft Learn "Deploy to Azure App Service by using GitHub Actions" (OpenID Connect) and GitHub Docs "Configuring OpenID Connect in Azure". The identity gets Website Contributor on the web app only.

OIDC subject: the most common failure

The credential's subject must match the token exactly. Here it is the production environment: repo:ORG/REPO:environment:production. GitHub Docs note that repositories created after 15 July 2026 (or renamed or transferred after it) use a new immutable subject format that includes owner and repository IDs. The Microsoft Learn pages don't cover this yet. Check the real claims with github/actions-oidc-debugger and set the subject to match. Also confirm the Node.js runtime string with az webapp list-runtimes --os linux.

Branches, tags and fallbacks

  1. Tag the clean starting point: git tag demo-start && git push origin demo-start.
  2. Create demo/not-found-message with the deliberately unsafe handler, and demo/add-date-helper with the vulnerable dependency (Act 4). Push both, but open their pull requests only on the day.
  3. During rehearsal, save the finished results as fallback/order-lookup-api and fallback/agent-lookup-page, and keep one Copilot pull request as a draft.
  4. Reset after each rehearsal: because the ruleset protects main, temporarily disable it (or use a bypass role), run git push --force origin demo-start:main in the demo repository only, and turn the ruleset back on. Then close rehearsal issues and pull requests, and redeploy the baseline.

Room and AV

  • Projector or screen at 1080p or better; presenter laptops tested with the venue's cable or adapter.
  • Wired network or a dedicated hotspot for the demo machines; the guest Wi-Fi tested with github.com.
  • Microphones for presenter and audience; a timer the presenters can see.
  • Whiteboard or flip chart for the parking lot and the value/feasibility grid.
